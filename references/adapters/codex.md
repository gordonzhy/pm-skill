# Codex 执行环境适配

本文件只在 Codex 环境中使用。本文只载入执行车道、回调和模型路由；[初始化](../manager-session.md)、[PMO 配对](codex-pmo.md)、[观察与监测](codex-monitoring.md) 分别按需读取。工具名称是适配协议，使用前以当次暴露能力及约束为准；**当前基线 `codex-cli 0.163.0` 的模型可见协作工具为 `spawn_agent`、`followup_task`、`send_message`、`wait_agent`、`interrupt_agent`、`list_agents`（`multi_agent` 指令）**，旧文档的 `codex_tui.*` 仅作历史兼容。未在其他环境验证的唤醒、信任或模型能力，不得直接套用。项目事实与验收仍遵循上级 [任务系统规则](../task-system.md) 和 [派发与验收](../delivery-loop.md)。

## 执行车道与派发

执行车道对应专属于一个仓库任务 ID 的独立执行上下文；工作树是否隔离遵守项目写入策略。当前 CLI 的模型可见协作工具属于 `multi_agent` 团队：`spawn_agent` 创建子代理，`followup_task` 给已有代理新任务并触发回合，`send_message` 只向运行中的代理传消息、不触发回合，`wait_agent` 等待团队成员变化，`interrupt_agent` 中断成员，`list_agents` 列名册。`spawn_agent` 创建的是当前会话内的团队子代理，不能直接当作旧版独立 Codex CLI 线程；真实创建/恢复/读取/唤醒行为见 [工具映射与能力验证](#工具映射与能力验证)，未验证前不得宣称车道可用。

新建授权车道优先用 `spawn_agent`；仅恢复同一任务未结束的原车道时用 `followup_task`（触发新回合），代理仍在运行时可用 `send_message` 传有界补充（不触发回合）。`send_message` 不触发回合，不能假定能唤醒空闲执行者或空闲经理；唤醒能力必须按“工具映射与能力验证”实测，未验证前不得宣称。若当前宿主未暴露所需工具或调用被拒，准备精确派发并说明工具限制，不由经理代做。初始提示遵守当前工具声明的长度限制（工具限制为1,000字节时按此上限），指向任务详情和交接规则；取得真实会话/派发 ID 后发送有界补充。临时客户端/设置 ID 不是持久路由，不能代替执行线程 ID。执行者收到经理线程 ID、派发 ID 和回调路径后才算完成登记。

CSV 当前结构中的 `execution_thread_id`、`execution_turn_id`、`manager_thread_id`、`manager_turn_id` 是 Codex 会话路由字段；`dispatch_id` 是稳定派发身份。工具返回的子代理名/ID 与 CLI 会话 UUID 不是同一标识，登记前必须核验真实 ID 来源。观察中的活动状态不写进仓库，而从用户级运行缓存按已登记 ID 关联。归档车道仅作历史，不解档复用；替代同一未完成仓库任务的车道不取消原授权。若会话创建工具另要求用户明确请求，应说明这是工具能力限制，准备派发并继续无关的已授权工作。

派发并确认路由与回调后，可用 `list_agents` 取一次名册快照，处理即时返回，再结束经理回合；不要反复长等待执行完成，需要等待变化时用 `wait_agent` 并优先较长等待而不是轮询。执行者在最终用户回复前用 `send_message` 发送终态回调；`send_message` 不触发回合，只有当前宿主实际支持且已实测能唤醒经理时才作为直接回调，未验证时回调缺席由按需配置的恢复监测辅助。经理被唤醒后按完整登记名册核对，单个成员返回不代表批次完成。需要具体证据时读取任务卡、交接/回调原文与候选报告；当前没有已验证的“读取其他会话全文”模型可见工具（`list_agents` 只列名册，CLI `codex agents` 只浏览会话），不得编造 `read_thread` 等价能力。纠正则发给原执行会话。已结束/已归档车道只在核对同任务历史路由或替代检查点时读取。不能将唤醒结论推广到 `send_message` 默认唤醒、`codex queue` 或未验证的 CLI 会话命令。

### 工具映射与能力验证

旧 `codex_tui.*` 名称只作历史兼容，不再写成当前可用。映射如下：

| 旧 `codex_tui.*` | 当前模型可见工具/命令 | 迁移结论 | 验证状态 |
| --- | --- | --- | --- |
| `create_thread` | `spawn_agent` | 新建执行车道改述为 `multi_agent` 团队子代理；不再声称创建独立 CLI 线程 | 部分验证：工具名与 `multi_agent` 声明已验证；真实创建、返回 ID 与并发槽位行为未验证 |
| `send_message_to_thread` | `send_message`（仅运行中传消息，不触发回合）；触发新回合用 `followup_task` | 续行拆分为“传消息”与“触发回合”两种语义 | 部分验证：声明已验证；真实投递、空闲唤醒与跨回合路由未验证 |
| `read_thread` | 无已验证等价；`list_agents` 只列名册，CLI `codex agents` 只浏览本机 daemon 上的会话 | 证据改由任务卡、交接/回调原文、候选报告承担 | 未验证：无模型可见读取工具 |
| `wait_threads` | `wait_agent` | 等待团队成员变化；批量等待改为逐次/多轮等待 | 部分验证：声明已验证；一次等待是否覆盖全部成员及超时语义未验证 |
| `set_thread_title` | 无已验证等价 | 标题能力缺失不等于任务受阻；身份用显式登记的真实 ID | 未验证：无模型可见命名工具 |

使用前在当前宿主重新发现可用能力：可用 `codex --version`、`codex features list` 和命令帮助核对 CLI；模型可见工具及其调用约束以当前会话实际提供的声明为准。CLI 命令存在不代表模型可直接调用，也不能证明创建、恢复、读取或唤醒已经通过真实运行验证。

| 能力 | 当前状态 | 边界 |
| --- | --- | --- |
| 创建执行上下文 | 部分验证：声明已验证，行为未验证 | `spawn_agent`；真实创建与返回 ID 未验证 |
| 恢复/续行 | 部分验证：声明已验证，行为未验证 | `followup_task` 触发新回合；`send_message` 仅运行中传信 |
| 读取会话全文 | 未验证：无 | 只有名册与任务文件/报告证据 |
| 批量等待 | 部分验证：仅单次等待声明 | `wait_agent`；批量语义未验证 |
| 回调唤醒空闲经理 | 未验证 | `send_message` 不触发回合；`callback.wakeupVerified` 保持 false |
| 中断成员 | 部分验证：声明已验证，行为未验证 | `interrupt_agent` |
| 名册快照 | 部分验证：声明已验证，行为未验证 | `list_agents` |
| 会话标题/命名 | 未验证：无 | 不影响派发与验收 |

未验证项不得写成已通过：真实 Codex 模型会话中的创建、恢复、读取、批量等待、唤醒与路由登记均未实测；本文只确认工具名和声明边界。

### 执行会话内的验收子智能体

主执行会话可用当次宿主支持的子智能体工具发起独立验收；当前基线用 `spawn_agent`，其声明提供 `fork_turns` 参数。使用 `"none"` 时不传父会话历史；声明还说明完整历史 fork（省略或 `"all"`）会继承父模型与推理强度且不接受覆盖，只有用户、`AGENTS.md` 或技能明确要求时才设 `model`/`reasoning_effort`，同时把 `fork_turns` 设为 `"none"`。上述是工具声明语义，真实上下文隔离行为未验证。验收提示只含目标/标准、候选、必要环境与权限边界、报告路径；黑盒场景不传源码、自测结果、修复原理。真实子智能体 ID、候选与隔离方式写入报告，不写作 CSV 主执行路由；经理不直接协调这些子智能体。

子智能体交原始报告给主执行会话，普通修正和复验在任务内部完成。若工具仅支持继承完整历史，改用新独立验证会话；若连独立上下文也不可用，明确交付缺口，不能声称已独立验收或把检查转给经理。上下文隔离不能证明文件权限隔离，需分别按任务风险说明。不擅自改变用户指定模型或绕过工具授权限制。

### 回调协议

终态包最多四行，只包含终态身份、提交/检查点、简短变更范围、关键检查和确切关注点：

```text
EXECUTION_CALLBACK · <completed|blocked|needs-decision> · <TASK-ID> · <DISPATCH-ID>
commit: <sha|none>; scope: <简短范围>
checks: <简短的通过/失败/未运行摘要>; report: <原始验收报告路径>
attention: <none|具体阻碍或决策>
```

用户在执行会话解决待决事项后发送：

```text
EXECUTION_DECISION_RESOLVED · <TASK-ID> · <DISPATCH-ID>
decision: <一行所选方向>
scope: <in-scope|expanded>
```

先完成仓库写入与验证，再把回调作为最终回复前最后一项工具流程。普通传输失败且当前授权允许重试时，最多重试一次纯回执行；自动审批/授权拒绝则立即停止该披露通道，不自动重试或更换载荷/目的地，保留本机交接供经理拉取；不绕过工具限制、不推测失败原因、不让用户代传。传输失败本身不改变仓库任务状态或用户参与分类。默认仅最终交接一次；中途仅满足[回报粒度](../worker-handoff.md#自主处理与回报规则)的条件才发送一次有界 `EXECUTION_MILESTONE`（任务/派发/阶段/候选/报告入口），不伪装 completed；后续仍在原授权内时继续执行，不等待经理回复。普通工具调用、局部修改、自测失败后修正或子智能体单项发现不回调经理。同一问题的自主处理与时限遵守[执行交接](../worker-handoff.md#自主处理与回报规则)。达到约定时限但仍能继续时，用一次非终态 `EXECUTION_MILESTONE` 汇总问题、实际影响、已尝试路径/证据、已耗时间和下一步，注明“无需决策，继续自行处理”；仅有明确解除条件的真实阻碍或需决策事项才用 `blocked` / `needs-decision` 终态，阈值进展不能伪装成终态。同一任务/派发跨阶段、问题及消息类型（包括 `EXECUTION_MILESTONE`、`blocked`、`needs-decision` 和主动询问回复）共用上次实际成功发送时间，相邻非最终汇报至少10分钟；不足时保留合并，首次无前次报告不等待，最终结束交接立即合并待报事件。10分钟不是定时汇报周期，1小时问题阈值也不豁免；不新增 sleep/服务，受保护动作先暂停。每个派发约定的业务成果、同一问题的首次阈值回报、终态转换或已解决决策最多一个成功回调；这只是去重上限，不是逐项发送要求，按任务 ID、派发 ID 及具体阶段/问题/事件类型去重。回调是证据，不是验收权；经理只核对任务、线程、派发、候选、原始验收报告及流程合规，不重复执行具体检查。

## 只读状态采集

需要状态、继续、派发、恢复或验收时，优先一次运行本地采集器，随后按具体证据缺口读取任务、报告或回调原文：

```bash
node <project-manager-skill-dir>/scripts/collect-project-state.mjs --repo <repository-root> --compact --max-ready 3 --task <task-id>
```

`--compact` 限制 Git 输出和详情片段，保留计数、路由、依赖、运行观察及完整校验结果；章节名称不匹配时返回最近章节，避免空摘要迫使全文重读。需要完整差异时再单独查询指定路径。不指定 `--task` 的接管可先看全局；可重复 `--task`，不指名则看项目全局；`--max-ready 0` 隐去就绪切片。仅验证昂贵或不安全时使用 `--no-validate`，本次不涉及运行恢复时可用 `--no-hook-check`。采集器返回任务与依赖、匹配的会话缓存、Git 状态、Hook/监测器提示和验证结果。`nextThreadReads` 指向需检查的线程，`registeredManagerThreadIds` 只是路由核对。缓存行、监测器锁和验证结果分别是观察、运行提示和结构检查，均不构成任务验收或授权。

## 当前 Codex 模型路由

仓库指令定义任务如何归入常规、复杂或高风险类别；本地 `.env` 可选设置 `PROJECT_MANAGER_MODEL_ROUTINE`、`PROJECT_MANAGER_MODEL_COMPLEX`、`PROJECT_MANAGER_MODEL_HIGH_RISK`，以及对应的 `PROJECT_MANAGER_REASONING_*`。派发前运行 `node <project-manager-skill-dir>/scripts/project-config.mjs --repo <repository-root>`，只读取这些白名单字段。未设置的类别按当前可用环境和任务风险选择，不从其他项目继承模型值；用户明确指定的模型优先，若不可用先说明。

模型选择取决于任务所需判断、风险和可验证性。输入精确、写入有界且有客观检查的机械工作可使用较低成本资源；诊断、设计、集成、共享契约、安全或实质评审需要相应能力。当前选择不足时，只升级未解决的工作并保留已有证据；不为换模型新建会话。派发记录模型、强度和简短理由；影响成本、质量或范围的变更应报告。
