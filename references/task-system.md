# 任务索引与生命周期

修改任务前，阅读最近的 `AGENTS.md`、目标仓库的任务索引与规则、受影响任务详情。本文件说明当前随 Skill 提供的 CSV 后端；其他仓库可采用等价的任务后端，但必须保持唯一真源和可验证生命周期。运行环境怎样实现会话路由与观察，由环境适配说明。

## 唯一真源

- `TASKS.csv` 是项目任务与路由的唯一索引，列依次为：`id,status,priority,boundary,title,dependencies,executor,created_at,modified_at,detail_path,dispatch_id,execution_thread_id,execution_turn_id,manager_thread_id,manager_turn_id,recovery_turn_id,recovery_state,recovery_state_at`。现有 `*_thread_id` 字段是兼容性路由字段；适配器将其映射到当前环境的稳定执行/经理标识。观察中的运行状态不成为任务事实。
- 每任务恰有一份 Markdown 详情，其仓库相对路径来自 CSV 的 `detail_path`。范围、完成标准、阻碍、进度、交接、验收证据和输出留在详情中。遵守仓库归属约定，不从任务 ID 前缀猜路径。
- 仓库定义交付阶段时，未终结详情应写当前阶段及允许值；除非有意修订结构，不新增 CSV 阶段列。
- `TASKS.html` 是从模板生成的固定只读前端，不是第二份任务快照。页面读取任务 CSV，服务可在数据变化时用事件提示重读；不定时轮询或以显示状态改账本。普通任务、运行状态、恢复元数据变化不重建 HTML，模板变化时才重建。呈现行为由 [看板呈现契约](dashboard-presentation.md) 管理。

## 项目任务编号前缀

每个项目必须拥有独立、稳定的任务编号前缀。采用 `<项目前缀>-<流水号>`，例如 `ATLAS-001`、`ORBIT-001`、`NOVA-001`；同一工作台内，不同项目不得复用前缀。前缀使用大写字母及数字、以字母开头，流水号按项目现有规则递增，符合当前 CSV 校验格式。不要为多个项目统一使用 `TASK-`、`DEV-` 等通用前缀。

项目专属前缀及允许的子前缀写入仓库 `AGENTS.md` 或等效项目指令。若需要按边界细分，可采用 `ATLASCORE-001`、`ATLASWEB-001` 等仍属于该项目的前缀；不要改为当前校验器不支持的多段连字符编号。经理初始化/接管、新建任务前核对本项目编号规则，并在多项目管理时核对与其他登记项目是否冲突；缺失或冲突时先明确专属命名空间，再创建新任务。只读查看可以继续。

新任务、CSV 依赖、详情标题/路径、派发与交接引用必须使用同一完整 ID。前缀不是任务类型、授权或路径规则，不能据此前缀猜文件目录。历史编号保持稳定：发现重复前缀时记录冲突与新任务编号规则，不直接批量改历史 ID；确需迁移时单独确定范围，同步核对 CSV、依赖、详情、证据链接、派发/回调及外部引用。

唯一前缀帮助人读，但不替代技术隔离：工作台仍使用 `project_id + task_id` 作为身份，兼容历史重号且不合并同名任务。重号/旧前缀测试夹具应保留为兼容性测试，不作为新项目的命名示范。

## 类型与测试链接

CSV可在原列末追加`task_type`，允许需求、设计、开发、测试、部署、管理；旧表及空类型兼容显示未分类，不从标题猜类型。新任务明确分类，详情用`- 任务类型：测试`等同步；类型只是主要交付分类，自测仍归开发，部署类型不授予部署权限。测试方式、范围与测试清单链接只在详情维护，见[independent-testing.md](independent-testing.md)。标为测试的新任务由验证器检查清单结构；准备阶段允许尚无执行结果，已完成必须有实际轮次及报告。历史任务按需迁移，不为分类批量审计。

## 状态与任务决策

- 保留仓库稳定 ID 和归属。先建详情，再加 CSV 行；标题和管理元数据同步，不合并独立负责人工作。
- `created_at`、`modified_at` 用带秒数与时区的 ISO 8601。新建时都设置，不改 `created_at`；CSV 行或详情实质变化时更新 `modified_at`。纯前端读取与渲染不改时间。
- 依赖仅写 `[]` 或 `[TASK-ID, TASK-ID]`；外部批准、人、许可和证据等非任务条件写在阻碍章节。拒绝未知、重复、自依赖或环。
- 状态只有 `待办`、`进行中`、`待确认`、`受阻`、`已完成`、`已取消`；不加估时、目标日期或交付承诺。执行会话正在集成、修正或复验，以及经理正在审查验收报告时仍为 `进行中`；执行已交付且等待经理开始审查，或有具体问题已向用户提出时可设 `待确认`。详情明确等待谁、交付证据或具体问题、以及确认后的下一步；不能用待确认表示未派发、普通等待或用户暂停。
- 用户明确要求暂停或停止未完成工作时，先确认执行者停止，再按仓库状态契约记录不可自动派发的暂停状态；本 CSV 后端用 `受阻`，在详情中注明“用户暂停”、已保留的成果和仅凭用户明确恢复指令才能解除的条件。暂停不自动生成待确认通知；旧派发路由只作追溯，不表示会话正在等待或执行。收到恢复指令后先核对授权、现场和写入归属，再转回活动状态并派发；不因其他任务完成而自行恢复。
- 只有 `待办`、所有依赖 `已完成` 且无真实阻碍才就绪。先遵循仓库交付阶段，再按优先级和最短可运行关键链选择。并行任务须独立且写入不重叠。非阻断评审意见按归属和阶段合并为最少可一次验收的后续任务。
- 派发前设置 `进行中`，登记稳定派发 ID、执行与经理路由。每个任务使用自己的独立车道，不同任务不共用或顺序复用；环境观察可选，缺失不能改变任务状态或依赖计算。恢复观察器只可更新通知去重元数据及相关修改时间，不改状态或详情。
- 历史兼容字段 `recovery_turn_id,recovery_state,recovery_state_at` 曾表示恢复通知代次与去重；新应用将这些运行记录保存在自己的状态目录，不再写回。旧格式说明：`recovery_state` 可为 `pending`、`sent`、`warning-sent`、`warning-muted`。`warning-muted` 仅兼容历史记录，不再创建永久消音，适配器最多沿用一小时。新暂停使用下面的有期限标记；警告或缓存状态均不证明执行空闲、失败或完成。
- 执行者交接只是待验收证据。完成声明在经理实际核验期间仍是 `进行中`；等待经理开始审查或需要用户决定时设 `待确认`，核实无法推进才设 `受阻`。只有经理设 `已完成`；纠正保持活动，待确认获决定并继续执行前才恢复活动。
- 唯一详情持久记录结果、变更范围、完成标准与证据、验证、重要假设和限制、风险、后续、用户交互事实及派发/执行标识。链接成果而不复制原始日志或整段执行记录，不另建任务状态真源。外部阻碍须写清责任人、具体行动与环境、完成信号、备选及必要安全约束。索引状态不代表外部批准、专业判断、许可或生产证据。

## 经理处理执行停滞提醒

经理主动停止、暂停或撤回执行时，必须在本轮核对成果并落实状态、原因、下一步及恢复条件；不能把自己已知的变化留给后台兜底提醒。后台程序负责故障检测与恢复，经理不巡检进程健康。

经理先核对最新执行回调与成果，再记录明确决定：尚不应启动或等待排期改为 `待办` 并说明启动条件；应该推进但有真实阻碍改为 `受阻` 并说明解除条件；已交付等待经理审查或用户决策改为 `待确认` 并明确等待对象。状态及详情同步后校验，监测器不再检查这些非活动任务。通知排队成功不是经理已处理，也不自动改状态、重派或恢复工作。

确需保持 `进行中` 且暂时允许执行会话不活动时，使用 `pm-server monitor pause`，提供原因、未来到期时间和操作者。暂停只存应用运行数据，不自动写任务日志；经理对项目有影响的暂停决定仍须自行记入任务日志。

暂停绑定本次派发和会话轮次，到期、派发或路由变化后恢复检查。提前恢复使用 `pm-server monitor resume`。历史 CSV 的 `monitor_pause_*`、`recovery_*` 字段仅作为旧格式兼容，由显式迁移处理；新应用不写回或自动清理这些字段，不代写经理决定。

## 任务粒度与追加需求

同一交付目标、负责人/写入归属和验收边界内的相似或简单改动，优先在原任务变更需求，不为每个反馈、参数调整、控件或内部步骤拆新任务。变更先更新当前范围、完成标准、必要的依赖/影响，再追加任务日志，并交给该任务原车道。不能只在聊天中追加而不改任务卡，也不以“并入旧任务”绕过实质范围、授权或专业独立性。

有独立目标、独立负责人、不同验收边界或必须单独追踪的依赖/风险时新建任务，并使用专属车道。已完成任务追加同范围改进时，记录重开原因、保留旧验收证据，复核已使用其成果的下游影响；按真实条件恢复待办/进行中，不能一边追加未完成工作一边继续声称整项已完成。历史共享车道不批量改写为虚假独立路由，后续派发按新规则安排。

## 任务日志是任务卡强制项

每份详情必须有非空的 `## 任务日志`，从创建开始维护。经理是中央日志的唯一写入者；执行者在阶段交接汇总关键事件和证据，经理及时追加；真实阻碍、范围/授权变化和用户决定即时记录。普通工具步骤及已在执行会话修复的失败不逐项唤醒经理，细节保留在过程/验收报告，中央日志引用并保留关键失败与修正，不能只在收尾补一条“完成”。日志随实质变更同步 `modified_at`，保持与当前范围、状态、路由、阻碍和证据一致。缺日志、空日志或关键事件未记时，不派发或关闭，先补齐真实记录。

从本轮接续起及时覆盖创建、需求/范围/完成标准及依赖变更、派发/车道替代、关键交付或检查点、验证结果（含失败及修正）、阻碍/暂停/恢复、用户问题和决定、经理验收、重开与关闭。每条包含实际发生或补记时间（带秒与时区）、记录者、事件、内容与结果/影响、证据或依据；记录路由变更时写原/新身份。新事件追加保留历史；错误用后续纠正说明，不删除早期失败或用新结果冒充原验收。一条只记实质变化与结论，简短正文链接证据；不复制历史章节、详细方案、反复声明未变边界或粘贴原始运行日志、整段对话与秘密。

新日志采用本章节内单一YAML代码块，字段、事件类型及示例见 [结构化任务日志](task-log.md)，仅在实际记录或维护日志时读取。日志和任务说明仍在同一Markdown文件，不单独维护日志文件。

历史逐条/表格日志兼容原文展示；按需依据可核实材料补记或迁移，注明补记时间与历史时间未知部分，不编造事件或自动批量改真实项目。历史缺项可用一条真实的接续记录指向原材料，不强制逐章迁移为事件；关键里程碑按证据补记。校验器分别检查结构化日志的字段、类型、ID、时间及依据，或旧日志的有效带时区记录；格式错误的YAML不能用旧记录绕过。日志是否充分及时及覆盖本轮关键事件仍须经理核验。

## 同步与验证

`<project-manager-skill-dir>` 指已安装 Skill 的真实位置，`<repository-root>` 指拥有目标 CSV 的仓库目录；不要猜仓库里另有 Skill 副本。索引或详情元数据变化后必须校验。仅在首次缺少 `TASKS.html` 或模板变化时先生成，再校验；普通任务变化无需生成：

常规更新只执行：

```bash
python3 <project-manager-skill-dir>/scripts/validate_tasks.py <repository-root>
```

首次缺少前端或模板变化时，在校验前另执行：

```bash
python3 <project-manager-skill-dir>/scripts/generate_tasks.py <repository-root>
```

脚本在任意工作目录均可运行：模板相对 Skill 定位，任务数据与输出相对目标仓库定位。验证包括 CSV 结构、路由元数据一致性、时间、ID 与路径唯一性、详情元数据、依赖有向无环图、状态及前端模板新鲜度。错误表示任务系统工作未完成。`ACTIVE`、`READY`、`CONFIRM`、`BLOCKED` 是计算视图。详情路径由 CSV 决定，验证器拒绝不安全、重复、缺失或未登记的任务形态 Markdown，不假定固定产品名和目录。 自动发现仅覆盖当前项目：Git仓库使用已跟踪文件及未被忽略的未跟踪文件；嵌套目录存在独立 `TASKS.csv`、`project-manager.config.json` 或 `.git` 时不混入父项目。非Git环境或Git查询不可用时退回文件系统发现，仍保留嵌套边界。CSV明确登记的详情始终校验，不因忽略规则或嵌套位置跳过；同项目发现的未登记任务卡仍报错。

可选运行观察只与当前任务登记的会话/执行标识关联；缺失或过期应显示未知或过期，不能回退为旧的项目侧运行状态。任务索引模块不制定卡片顺序、布局、筛选或浏览器交互；呈现请求不得修改任务状态语义。
