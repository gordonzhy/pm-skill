# 独立测试与问题闭环

## 任务内验收与经理决定

默认一个任务、一个主执行会话。主执行者完成实现和自测后，启动不继承实现历史的验收子智能体，独立执行本任务的验收单；普通缺陷在执行会话内部修正/复验，不新增任务、不把子智能体纳入经理直接调度名册。跨多个任务且有独立交付范围的系统测试仍可单独立项。子智能体不能兼任修复作者或修改中央任务文件；它报告事实和检查结论，最终批准仍属于经理。

验收报告至少写任务/派发 ID、候选提交或产物身份、验收者实际身份与上下文/访问隔离方式、标准逐项覆盖、实际环境与操作结果、证据入口、首轮失败及修正/复验关系、未测/受阻、开放问题和结论。格式按风险取最小充分形式，不为普通任务强制整套测试清单文件。候选改变后补验受影响部分；保留验证者原始报告，不由作者改写为通过。

经理检查报告是否来自正确候选、是否覆盖标准、是否有足够的真实执行证据和所需独立性，以及未解决项是否符合放行门槛，作出通过、退回或受阻决定；不执行具体检查、不重新跑测试或浏览器、不逐条复现问题。报告缺失、证据不一致或隔离不足时退回执行会话补齐。专门的安全、专业、外部或受保护验收要求仍按项目契约满足，不能用一般子智能体报告替代。

## 任务、问题与放行

一个测试任务对应一套场景/问题记录，可含多个问题；任务管理执行范围、负责人和交付，问题管理具体发现及处理。经理分诊后先判断能否合并到相同目标/归属/验收边界的已有任务；确需独立追踪时才创建最少必要修复任务：多个问题可合并修复，一个问题也可关联多个修复任务。修复任务详情反向链接具体问题ID。开发任务中的自测仍归开发。需求、设计、开发、测试、部署、管理是主要交付类型，不代表状态、读取权限或部署授权。

测试任务完成表示本轮约定范围已执行、未测/受阻明确、清单合格且经理已分诊；不表示产品通过。开放问题可以保留，产品放行由经理按阶段验收标准判断。修复完成只进入待复验；原问题以新版本的独立表现证据关闭。暂不处理须有决策人及理由；重现沿原编号重新打开，不删历史。重复问题用duplicate_of关联唯一正式记录：同清单用问题ID，跨清单用`evidence/.../issues.csv#问题ID`，目标必须实际存在、唯一且不是另一重复项；自指与重复链拒绝，经理确认，不再重复派修。

## 黑盒信息隔离

独立黑盒体验执行者只接收用户目标、已确认预期、公开入口、固定版本标签、测试环境和投入/操作边界。不提供源码、实现说明、开发自测结论、疑似根因或修复原理；不用DevTools、内部日志/网络实现替代用户表现。修复复验只提供问题现象/步骤、可复验版本及必要用户预期。

用不继承实现历史的新子智能体或独立验证会话；只传必要验收输入，不能让已读实现的作者/审查会话冒充黑盒测试者。上下文隔离与文件访问隔离分别说明，不能因为新建会话就声称不可读源码。优先为执行车道限制为浏览器界面和证据输出能力、不可读源码的工作目录；若环境只能提示约束，明确记录“提示隔离，非资源强制隔离”，不能声称工具已阻断源码读取。主执行者负责建立并在报告中说明该限制，经理只检查所需独立性是否满足；不足时由执行会话补充隔离条件或报告能力缺口。实现/验收者的自测不代替独立黑盒任务。

`testing.py brief`仅输出用户场景、版本标签与公开入口，不输出实现材料；它不建立系统级隔离。测试者只描述所见、预期和实际影响，不猜根因/规定代码方案。没有可操作入口就报告受阻；HTTP、截图、开发口述不替实际操作。黑盒不能证明内部安全、释放或底层GPU正确，按需要另设适用检查。

## 最小持久记录

suite入口及其工件必须在仓库真实`evidence/`内（含symlink解析后的路径），与看板只读白名单一致。项目选择符合本地规范的`evidence/`内目录；经理在原任务详情写：

```markdown
- 任务类型：测试
- 测试方式：黑盒体验
- 测试清单：evidence/<task>/<run>/suite.json

## 测试交付入口
[报告](evidence/<task>/<run>/report.md)
[场景](evidence/<task>/<run>/scenarios.csv)
[问题](evidence/<task>/<run>/issues.csv)
[轮次](evidence/<task>/<run>/runs.jsonl)
```

以上链接按仓库根相对，经理维护详情，测试执行者不跨写元数据。看板汇总从问题清单读取，不维护第二份状态。项目选用更小格式可以调整后端，但不能丢版本、未测范围或问题闭环。

- `suite.json`：task_id、method（黑盒体验/接口/代码/性能）、target、version（固定公开版本标签）、environment、owner（本轮唯一清单writer）、access（黑盒为public-only）及report/scenarios/issues/runs仓库相对路径。初始化的待填写值必须在派发前完成。
- `scenarios.csv`：scenario_id、goal、steps、expected。至少核心完整用户旅程，允许自由探索时补稳定场景ID。
- `issues.csv`：issue_id为`<task-id>-P...`、scenario_id、kind（缺陷/体验建议/待确认）、severity（阻断/重大/一般/轻微）、summary、steps、expected、actual、frequency、evidence（仓库路径，以分号分隔）、found_run、status、decision（决策人及理由）、repair_tasks（分号分隔）、duplicate_of、verified_run。严重度按任务阻断/错误结果/影响范围判断。当前状态允许待分诊/待修复/待复验/已关闭/暂不处理。
- `runs.jsonl`追加轮次，不覆盖原结果。每行含run_id、version、environment、at（带秒及时区）、scenario_results（所有场景含通过/发现问题/受阻/未测）、issue_results（问题ID→{result:通过/仍存在/受阻/未测,evidence:[路径]}）。首次观察与复验都留实际证据；关闭关联成功且有证据的复验轮。新独立任务继续关联原清单，避免重编问题ID。
- `report.md`：实际执行、版本/环境、范围、结果、限制和下一动作；零问题明确写零，不能空白表示全部通过。没有发现不等于无缺陷。

测试者单writer维护这些工件；经理通过原任务分诊回执给处理决定，由当前writer落实。执行轮结束需改清单时先交接writer，不同时编辑。原始轮次只追加，当前问题状态可更新。黑盒输出目录与可读输入分别登记；清单内容可能包含用户数据，遵原任务数据权限，不自动外发。

## 脚本与经理接收

```sh
python3 <skill>/scripts/testing.py --repo <repo> init --task <ID> --directory evidence/<task>/<run> --method 黑盒体验
python3 <skill>/scripts/testing.py --repo <repo> brief --suite evidence/<task>/<run>/suite.json
python3 <skill>/scripts/testing.py --repo <repo> validate --suite evidence/<task>/<run>/suite.json --completed
python3 <skill>/scripts/validate_tasks.py <repo>
```

init拒覆盖既有清单。准备阶段允许无运行/问题；brief拒待填写输入。validate检查唯一编号、版本/轮次、证据路径、状态、修复与复验关系；独立validate与任务验证器使用同一修复任务存在性规则：非空repair_tasks需能读取并校验TASKS.csv；缺索引/坏索引不能默认为通过，零问题准备不要求额外索引。任务验证器同时核任务身份、测试方式、详情链接。机器不能证明证据真实、隔离未被违反、问题严重度合理、历史未被重写或产品可放行，经理仍需核对报告/证据一致性与流程合规；缺口交执行会话补验，不由经理复做具体检查。未经复验不能关闭；无新增工作不唤醒作者。先跑完真实首测→分诊→修复→复验再评估方法收益，不固定次数、工时或费用为通用阈值。
