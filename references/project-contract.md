# 可移植的项目契约

将项目经理模式接入仓库或审计仓库是否支持它时阅读。

## 三层职责

1. **项目经理核心：** 角色、上下文边界、授权门槛、派发与验收闭环。
2. **任务后端：** 仓库任务结构、依赖、生命周期和确定性校验；当前 CSV/详情实现见 [任务系统规则](task-system.md)。
3. **执行环境适配与仓库指令：** 前者把车道、消息、等待、观察和模型映射到实际工具；后者说明本地任务真源、治理来源、架构/归属、允许行动及项目特有政策。

待办事实始终留在仓库权威任务后端。其他环境可换适配器，其他仓库可换任务后端；管理授权、证据与验收责任不因此转移。

## 最小任务后端与执行能力

自动派发前需要唯一任务索引、稳定 ID、每任务一份详情、状态/优先级/依赖/负责人/范围/完成标准/阻碍/输出/证据和持续维护的任务日志、经理评审期间仍活动且不释放依赖的状态、可计算的就绪/活动/受阻集合、串行中央写入路径，以及能拒绝未知依赖、环、元数据矛盾和虚假完成的校验。

执行环境须能为每个任务创建专属独立执行单元，并恢复同任务的原执行单元、登记真实稳定路由、传递有界终态交接、读取相关证据，并在并行批次中等待完整成员名册。适配器必须注明回调能否唤醒不活动的经理、观察数据的新鲜度与失效方式、消息失败怎样有限重试。缺少已验证能力时不能推定自动续跑或让用户充当内部中继。观察器与恢复监测可选，不代替直接交接或经理验收。不同任务 ID 不共用或顺序复用执行车道；已归档车道不恢复复用。看板运行时读任务真源，观察写入者不重建 HTML。

经理还应检查授权工作无人推进、交接/验收停滞、回调与状态冲突、普通确认被推给用户、控制规则反复造成浪费等运行缺陷。在已批准边界内修复最早有问题的层级并验证；产品方向、范围、架构/归属、外部或专业授权、生产/受监管数据、重大成本及不可逆高影响风险另行升级。

跨任务或跨边界持久工作须有可发现的治理来源，最小规则包含负责人、边界或不变量、验收证据、变更/例外路径。一次性、局部、低风险、可逆且已被现行边界覆盖的工作不必新增政策。若任务后端或执行适配缺失，先建立或提出最小基础工作，不能从文件名或散落叙述猜就绪状态。

仓库指定产品设计方法时，按仓库规则核对方向确认者、交付阶段、各阶段验收门槛与历史批准的适用范围；本 Skill 不替项目规定阶段名称、缺陷等级或放行条件。

## 项目级配置（`project-manager.config.json`）

新项目用宿主无关 CLI 初始化，不再手工拼任务文件：

```sh
node <Skill>/scripts/init-project.mjs --repo <仓库> --prefix <大写前缀> --name "<项目名>" [--group <分组>] [--force]
```

生成物：`TASKS.csv`（标准 18 列）、`<detailsDir>/<PREFIX>-001.md`（含合法结构化任务日志的示例卡）、`TASKS.html`、`AGENTS.md` 片段、项目配置。所有宿主都直接调用该脚本，没有宿主内命令入口。

配置是**单一入口**，固定放仓库根，`configVersion: 1`：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `project.name` / `project.prefix` | 是 | 项目显示名；任务编号前缀（`[A-Z][A-Z0-9]*`）。 |
| `project.group` | 否 | 工作台登记默认分组，缺省 `未分组`。 |
| `taskSystem.csv` | 是 | v1 固定 `TASKS.csv`（工作台/校验器入口）。 |
| `taskSystem.detailsDir` | 是 | 新详情卡默认目录（仓库内相对路径，缺省 `work-items`）。 |
| `taskSystem.statuses` | 否 | 状态词表；v1 固定 6 个状态，不能增删。 |
| `workbench.port` / `workbench.stateDir` | 否 | 本项目工作台/兼容看板默认端口（缺省 9999）与可选状态目录。 |

- 选择 JSON 而非 YAML：零第三方解析依赖，Node 内置 `JSON.parse` 与 Python、编辑器 Schema 都能直接读；项目配置只承载身份与确定性路径，不需要注释。
- 读取/校验只有 `scripts/project-config-v2.mjs` 一份实现，结构 Schema 在 `assets/project-manager.config.schema.json`；`validate_tasks.py` 在配置文件存在时调用它，配置损坏会让校验失败。
- `init` 幂等：已有 `TASKS.csv` 时不修改；`--force` 先备份到 `.project-manager/init-backup/<时间戳>/`；生成物先在临时目录通过校验才写入，失败不留半成品。
- 既有仓库根 `.env` 白名单（`PROJECT_MANAGER_MODEL_*`、`PROJECT_MANAGER_REASONING_*`、`PROJECT_MANAGER_PMO_THREAD_ID`）继续兼容；同一字段不再在 `.env` 重复定义，工作台端口以项目配置为准。
- 工作台登记：`pm-server project request --repo <仓库>` 可省略 csv/name/group，由项目配置补齐（显式参数优先）。

## 仓库指令建议

首次接入时，检查仓库根目录的 `AGENTS.md` 或等效指令是否给出以下项目规则；没有独立 `AGENTS.md` 的环境，可使用该环境实际会读取的仓库级文件：

- 项目专属任务编号前缀及允许的子前缀，与其他登记项目不冲突；历史编号迁移按 [任务系统规则](task-system.md) 单独处理。
- 任务真源、详情模式、后端和执行适配；中央文件的单一写入者与执行者允许写入的范围。
- 当前交付阶段、优先级或缺陷等级的含义、各阶段验收证据与放行门槛；方向由谁确认。
- **执行资源路由：** 哪类机械、常规实现、复杂设计或高风险任务使用哪些可用模型、推理强度或人员；何时升级、何时须报告成本变化，以及用户明确指定资源时如何处理。具体名称和额度属于仓库及团队配置，不写进通用 Skill。
- 部署、数据、外部通信、付费资源和不可逆操作的本地授权边界，以及需要独立验证的条件。

仅补与当前项目有关的规则，沿用已有权威来源，避免复制相互冲突的政策。缺少规则时，经理说明它会影响哪项派发或验收，核对现有约束后提出最小可用表述；在已授权的仓库管理范围内可修复明确缺口。涉及新的成本上限、方向、归属或高影响授权时交由有决策权的人确认。暂不需要该规则的状态查询或只读核查可以继续，不能因缺项擅自认定项目已选择某个模型或放行门槛。

具体端口与模型 ID 可放在仓库根目录的本地 `.env`，并确保它被 Git 忽略且未被追踪。仓库指令说明如何按复杂度/风险分类，`.env` 只给出本环境各类资源的具体值；未设置的项目使用适配器默认值。读取 `.env` 时只解析本 Skill 声明的字段，不执行文件内容，也不把其他环境或项目的取值写回仓库规则。

用户明确授权目标、任务或就绪批次后，为每个任务使用专属独立车道，按资源约束持续推进；执行会话组织实现、自测和隔离子智能体验收；经理检查流程及验收报告并独占最终关闭，批次全部协调和验收后再释放依赖。状态问题允许检查和恢复已授权内部协调，但不启动无关新交付。

每仓库记录执行环境默认选择：隔离工作树适合代码改动、高风险迁移、重叠文件和独立评审，并说明集成路径；共享检出只有写入范围可证明确实分离时使用；云或外部环境需要明确授权及返回路径。选择环境本身不授权部署、生产数据、外部消息、付费服务或破坏性操作。

## 明确接管与项目级经理

用户明确要求接管时由 `initialize-manager.mjs --repo <仓库> --manager-thread <真实ID>` 复用既有任务体系；标准账本缺失则自动以 `--empty` 创建。初始化不添加业务或示例任务，不隐含交付派发。目录及账本是否已存在决定创建方式，不代替用户选择管理对象。

项目配置可含 `manager: {threadId, registeredAt}`，分别为真实会话路由及带时区的登记时间。它使空项目也可登记经理，并供工作台和通知通道读取。任务行 `manager_thread_id` 保留任务回调语义；更新经理不改执行者、派发身份、任务状态或授权。同经理重复接管不刷新登记时间。
