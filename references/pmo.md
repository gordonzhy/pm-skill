# PMO 协作与经验闭环

首次创建/接管经理会话时，以及里程碑复盘、过程重复受阻或组织问题处理时阅读。

## 职责与归属

每个项目配一个用户可见的独立宿主 PMO 会话（不使用会话内子智能体或仅新上下文替代），经理接管时复用并刷新回调路由，不为每个任务另建 PMO。PMO 的工作是改进交付过程：检查关键路径与依赖是否合理、能否更早让用户看到产品、并行车道及共享写入是否得当、验证和授权是否与风险相称；检查代码模块、目录、接口和资产组织，以及文档真源、导航、版本归属与证据可发现性。以当前证据比较可行路径和代价，不声称证明了全局最优。

PMO 可以读仓库、任务与限定过程记录，写经理指定的复盘/改进文档或提议差分。经理独占任务索引、详情、看板及状态决策；PMO 不改这些文件、不直接指挥执行者、不自行批准或验收产品、不绕过依赖与授权。产品重构和文档迁移先成为具体建议，由经理核对既有授权与写入归属后派发；用户明确授权 PMO 执行特定项目文档改进时，在该范围内落实，不重复请求同一授权。本技能改进只提交维护建议，业务项目 PMO 同样不得修改源码、共享源、分发模板或已安装副本；实际维护须属于用户指定的唯一 Skill 维护项目并有明确授权，遵守[本技能维护归属](../SKILL.md#本技能维护归属)。用户记忆、配置、生产或外部系统不因“积累经验”自动获得写权限。

## 同步建立与持续参与

缺少独立会话能力或创建授权时，保留 PMO 未配对及其工作缺口，不默认降级或由经理代做；已验证的控制面工作可继续。经理配对时登记项目、PMO 真实会话标识、当前经理标识、输入与写入范围。会话标识按适配器保存；任务状态仍仅在原任务真源。首次检查使用紧凑状态、当前目标与主要欠项，禁止默认审计全部历史或启动产品测试。普通有界治理检查不机械拆成正式任务；形成独立复盘交付时按下节登记并使用专属车道。Codex 路由操作见 [PMO 适配](adapters/codex-pmo.md)。

持续优化由经理在日常管理中触发：发现关键路径绕远、重复验证/交接、用户迟迟看不到改动、范围漂移、共享资源冲突或同类阻碍反复出现时，向 PMO 发送一个有界问题。PMO 有工作时合并新增事实到同一复盘，不开重复批次；无新增事件时会话空闲是正常状态，不把它长期登记为“进行中”，不用忙轮询维持存在感。这里的持续是生命周期内反复参与，不意味着后台定时执行；未被验证的唤醒或监控不能假设存在。

## 较大交付后的主动复盘

较大任务包括跨车道/模块的集成交付、可供用户操作的版本、阶段验收、部署或重要架构/流程变更。任务整体仍未完时，已有实质阶段交付也可复盘，但输入必须标明已完成的阶段及开放项；不要把“执行者结束”或“候选源已准备”冒称整个任务完成。多个小任务共同形成一个里程碑时合并复盘；不以文件数或固定耗时机械判定。

经理在验收记录后主动创建或复用一个普通复盘任务：在既有索引登记真实派发、范围和该任务的专属执行路由，指向实际工件与过程记录；常驻 PMO 提供治理输入，不作为不同正式任务共用的执行车道。原产品任务已经合格的关闭与后续就绪工作不等待复盘；发现具体交付阻断才提升为对应问题。不能把永久 PMO 角色做成永不结束的活动任务。

交接最少包含：里程碑/任务和完成信号、已交付与未交付、关键调度/授权/验证决策、失败与返工证据、当前问题、允许输出目录和经理回调。PMO 先看这些有界输入，具体缺口再读原记录，不根据经理的结论写恭维式总结。

## 把经验变成改进

复盘写进项目约定的过程改进目录；没有目录时用 `docs/project-management/pmo/`，不另立状态账本。采用足以回答问题的短报告：

- 哪些做法有效、哪些造成等待或返工，分别有何证据；事实与推断分开。
- 下一次更短/更稳的执行路径，以及要保留的必要边界。
- 可落地的最小改进、预期收益、代价和验证信号；没有实质问题时明确无需改进。

每条建议同时注明“通用 / 项目专用 / 待验证”、证据及拟落地位置，合并在原报告行内，不增加分类审批表。方法与成本评价按 [小批交付与投入控制](efficient-delivery.md)，同时检查整体交付时间、返工、可获得的实际消耗及质量，不能把任务/文件/检查数量等同价值。

经理接收后对建议记录采纳/试行/不采纳及理由；控制面与项目知识记录在授权内更新，具体交付派发执行车道，需要新的实质决策时展示具体方案。落地工作用原任务系统跟踪，PMO 不另建待办清单真源。后续里程碑检查该改变是否真的减少等待、返工或提高交付质量，决定保留、修订或撤回。

## 通用与项目专用的落地边界

- **通用：** 去掉项目名称、端口、特定角色/资产、技术栈、品牌、负责人和当地授权约定后，仍能指导其它项目的交付决策。说明适用条件、收益与代价；这类优化可整理为本技能维护建议，由用户指定的维护项目决定是否纳入；分类本身不授权修改本技能。用户明确要求试行的通用方法可先在所属项目作为可调整原则落地，但不得声称已证明跨项目收益。
- **项目专用：** 依赖本项目产品目标、技术/资产管线、部署环境、角色权限或特定资源配置的措施，只改该项目已有契约或工程/过程文档。具体时限、并发数、模型与费用上限均属项目配置；不把它们复制到通用 Skill。
- **待验证：** 单次观察、根因未明或收益未知的判断留项目复盘，给下次验证信号；验证和抽象后再重新分类，不能直接变成通用强制规则。

混合建议拆成通用决策方法与项目实例分别落地；通用 Skill 不携带项目专用实例/路径/参数，项目文档引用 Skill 而不复制整套方法。落地前核现有目标文件和写入归属，不以分类为由扩大权限或另造任务真源。对一般性、固定强制规则的新增应有多次证据支持；没有收益的建议可以不采纳。

后续同类交付以实际证据决定保留、修订或撤回，复盘不再重复添加已存在的规则。不自动改用户记忆、不追加重复流程文档。复盘结束按正常交付回调；经理核验收口并报告关键改进，PMO 的建议不代替产品验收。

关键发现、决策与相关变更由经理同步到对应任务日志。
