# 结构化任务日志

仅在创建/追加日志、修复格式或维护时间轴时读取。日志唯一真源仍是任务 Markdown 的 `## 任务日志`；经理写入，执行者报告关键事件。不得另建一份 YAML 或重复维护手写摘要作为日志真源。

## 记录粒度与简洁性

一条日志只记一个实质事件：发生了什么变化、结果如何、依据在哪里。标题一句话，`detail`写1–2句新增事实，通常不超过120字；这是写作目标，不是截掉关键失败/决定的硬性校验门槛。具体方案、参数表、完整哈希、命令输出与长篇论证留原报告或任务说明，用依据引用，不搬进时间轴。路由放专用字段，正文不重复完整ID。

只在本次边界或结论确实变化时记录相关限制；不在每条重复全项目授权、未部署、未复验等通用声明。`impact`仅有新增影响时填写，不用固定免责声明填充。正常读取、重复通知、无新事实的等待不机械记一条；真实变更、关键失败及修正、阻碍/恢复、决定和验收不能省略。

维护日志从本轮接续开始及时记录，不为形式完整将每个历史章节转成新事件。旧卡缺日志时，在已有授权与真实依据内用一条简短的历史接续记录引用原材料即可；它只说明本次接续行为，不冒充旧工作新发生或重新验收。需要追溯的重要里程碑才按可核实材料单独补记。迁移计划、完整原文和原始历史保持可追溯，不复制成数十条长摘录，不自动重写真实项目记录。

## 格式与字段

章节内只有一个 `yaml`（或 `yml`）围栏代码块，版本为1。文件顶部元数据不承载事件历史。推荐示例：

````markdown
## 任务日志

```yaml
version: 1
events:
  - id: log-001
    at: "2026-10-14T10:00:00+08:00"
    actor: 项目经理
    type: requirement_changed
    title: 追加任务日志时间轴
    detail: 在原任务中增加结构化日志与详情页展示。
    impact: 更新范围和完成标准，继续原任务车道。
    evidence:
      - label: 需求依据
        ref: 用户本轮明确指令
```
````

每条必须有稳定且任务内唯一的 `id`、`at`、`actor`、`type`、`title`、`detail`、非空 `evidence`。正文使用真实内容，不填TODO/模板占位。每份依据有非空 `label` 与 `ref`，可选 `note` 保存行号、版本或原章节说明；`ref`只放纯路径、URL或来源文字，不能把“补记前第660行……”拼进文件路径。普通相对路径按项目根目录解析，明确的`./`或`../`按任务卡所在目录解析；HTTPS保持原地址。多行内容用 `|` 或 `>`，时间加引号，必须有秒和时区。

| 字段 | 用途 |
| --- | --- |
| `at` | 实际发生时间；未知时明确填 `null` |
| `recorded_at` | 补记时间；`at: null` 时必填，其他补记也应填写 |
| `impact` | 范围、依赖、交付或用户影响 |
| `result` | `passed` / `failed` / `partial` / `not_run`，用于检查结果 |
| `state_from` / `state_to` | 记录状态变化，不据此覆盖 CSV 当前状态；为准确统计时间分布，状态变化填写原/新状态和实际发生时间，不能用补记时间替代 |
| `route_from` / `route_to` | 替代执行车道时记录原/新身份 |
| `started_at` / `ended_at` | 可选的具体活动起止时间，均为带秒和时区的ISO时刻；成对填写，尚在执行时`ended_at: null`。`title`说明这段时间做什么，`detail`补充结果，不从相邻事件或补记时间推算工作区间 |
| `supersedes` | 更正所关联的旧事件ID；旧记录继续保留 |

事件类型固定为：`created`（创建）、`requirement_changed`（需求变更）、`dispatched`（派发）、`checkpoint`（检查点）、`verification`（验证）、`blocked`（阻碍）、`paused`（暂停）、`resumed`（恢复）、`decision_requested`（请求决策）、`decision`（用户决定）、`accepted`（验收）、`reopened`（重开）、`closed`（关闭）、`cancelled`（取消）、`route_changed`（路由变更）、`corrected`（记录更正）。未知字段、重复事件ID、非法日期/时区及缺依据均拒绝，不自行猜类型。

按发生顺序追加事件，界面自行按真实时刻倒序；相同时刻后追加的先展示。未知发生时间按补记时间排序，并明确显示“发生时间未知”；不能把补记时间冒充发生时间。修正追加新事件，关联旧ID，不覆盖失败、旧范围和旧验收。

## 兼容与展示

历史逐条/表格日志继续接受原有校验，在日志Tab原文展示并注明未结构化，不推测日期或自动编造事件。可以保留历史原文，在同章节追加一个结构化块；结构化块必须完整有效，旧原文不能掩盖新块错误。迁移依据可核实材料进行，不自动批量改真实项目；优先原文入口加少量关键里程碑，不逐章搬运。

详情弹窗独立“任务说明 / 任务日志”Tab。说明页不重复显示日志代码，日志页默认只显示时间、类型、记录者、标题与短摘要；检查结果和状态变化保持可见。完整正文、影响、依据与路由/更正信息收进逐条“展开”区域，原内容不删，截取摘要不能当作完整结论。失败突出显示；格式错误给明确提示，缺失显示无日志，读取失败显示失败，均不伪装成功或零错误。同一补记时刻且发生时间未知的多条记录默认分组收起，显示条数、未知发生时间及补记说明，含结构化失败结果时汇总失败数量，不伪装为当天的实际进展；展开后仍可逐条追溯。已知发生时间的历史事件按真实时间排列。旧原文默认收起，可展开阅读。安全文本渲染，危险协议不生成可点击链接。

Python校验、Node摘要与浏览器时间轴共用 `scripts/task-log.mjs` / `assets/task-log.js` 的解析和结构规则；依赖固定版本的本地 YAML 解析器，不从页面加载外部CDN。批量校验只启动一次结构化解析子进程，避免每张任务卡重复开销。解析错误不能跳过校验，结构通过也不能证明事件完整及时。

### 刷新与本地依据访问

同一任务后台刷新时，Markdown 未变化不重建日志；内容变化保留历史分组、单条依据和旧日志原文的展开状态，以及滚动位置、键盘焦点。切换任务重新开始阅读。

服务端从已登记任务卡的有效结构化日志中提取明确文件引用，逐文件开放只读访问；支持 `ref` 中的项目根目录路径、任务卡相对路径及旧行号注释，不开放整个目录、不递归发布报告内链接。文件必须存在且真实路径位于项目内；隐藏配置和仓库外符号链接不放行。外部 HTTP(S) 链接直接访问，不抓取、不登记成本地文件。HTML、SVG 等可执行文档作为附件下载。

旧任务的本机绝对路径不能直接拼接到 HTTP 站点根路径；前端须转换为任务专属的 `task-log-file` 入口。服务端核对原任务仍在 CSV 登记、日志有效且包含完全相同的引用，再读取项目内真实文件。对项目外仅额外支持当前技能 `references/` 下明确引用的 Markdown 说明文件，不开放其他本机目录或未引用文件；旧卡无须为此批量重写。


### 具体活动的执行过程

需要呈现“从第几秒到第几分几秒在做什么”时，执行者在关键活动边界记录实际开始/结束时刻、工作内容及依据，阶段交接交经理写入原任务日志。一次活动用同一条事件的 `started_at` / `ended_at` 表达，例如 `00:35 → 02:05 修改代码`；不需要把每个工具调用都变成中央日志。进行中活动可以先记录结束为null，完成时追加更正事件并用`supersedes`关联原记录。不能为填满时间轴倒推或编造阶段时长。

界面使用单行彩色图形时间轴，按真实日期与时分秒刻度定位活动区段和事件节点，悬停或聚焦时显示具体工作、完整起止时间和持续时长，平时不显示逐项文字详情；并行活动分别保留，不合并成串行。区间之间无记录时明确标注“这段时间未记录活动”；仅有事件时点的旧日志显示绝对时间节点及“未记录持续时间”，不能把两条日志间隔解释为前一项工作时长。任务总执行时间与活动过程的记录口径分别标明，活动记录不自动等同完整工时。
